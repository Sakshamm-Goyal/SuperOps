## Coding standards

Use typed Python interfaces and small pure domain functions. Perform decimal/unit conversion at explicit boundaries; inject clocks and provider adapters for deterministic tests. Pydantic models reject unexpected fields and invalid values. Domain exceptions map to documented stable errors; avoid catch-all success responses. Network clients need deadlines, cancellation, bounded read retries and useful redacted errors.

TypeScript sidecar uses strict checking and validates HTTP envelopes. Keep modifications to the vendored H-MEM reference small, attributed and accompanied by upstream-versus-local tests. Do not turn the six-day build into an H-MEM rewrite. No fake SDK classes: call interfaces verified from the pinned source or sponsor OpenAPI.

Use one migration system and test upgrade from a blank database plus the last supported schema. Schema and memory/vector version changes need an explicit upgrade/rebuild plan; never silently reinterpret old records. Use repositories for transactions and source adapters for external data. Avoid importing network clients at module import time or connecting with credentials merely by loading a model schema.

UI presentation derives from API state. Browser/session cache is disposable. Keep long-running work in durable jobs and use persisted event polling. Repeat form submission must not create duplicate actions. Hide write actions from read-only users but still enforce permission server-side.

## Agent and prompt changes

Version prompts, tool schemas, model identifiers and evaluation configs. Use structured outputs plus schema validation; distinguish unsupported structured-output capability from malformed model behavior. Do not perform unconstrained JSON repair that invents an action. A single bounded corrective attempt can re-request missing schema fields; repeated invalid output ends with explicit failure and consumes budget.

Prompt edits require relevant golden/eval cases, including the failure they address and a contrary case. Tune on development data only. Deterministic validators remain separate from the optimizer and critic. Show tool inputs/outputs, evidence IDs and concise cited rationale; private model reasoning is not a correctness artifact.

## Dependency and supply-chain procedure

On day one choose the supported versions in ARCHITECTURE, inspect official install docs/advisories, resolve Python/Node dependencies in clean environments, run model/sponsor/memory smoke tests, then commit lockfiles and runtime/container versions. Use reproducible locked installs in CI. Security scans are necessary checks, not proof that a package is risk-free.

ADK currently documents a LiteLLM compromise affecting versions 1.82.7/1.82.8 and a newer dependency floor. Do not copy those versions or assume any version outside the pair is automatically safe. Recheck the advisory when selecting the actual lock. This review did not inspect or install the user's existing environment. [ADK connector advisory](https://adk.dev/agents/models/litellm/).

Review licenses and generated dependency inventory. Avoid curl-to-shell, arbitrary remote setup scripts and unchecked postinstall execution. Read the Meterless starter setup process before vendoring. Prefer least-privilege credentials injected at runtime. CI for untrusted PRs receives no sponsor/cloud secrets.

## Proposed command contract

The following are target commands to implement and validate, **not runnable instructions today**. Once available, README must replace this proposal with exact prerequisites, versions and verified output.

| Intended command | Required behavior |
|---|---|
| `make bootstrap` | Locked dependencies and validated runtime versions; no cloud resources or secrets created |
| `make preflight MODE=connected_demo` | Check configured capabilities/auth/network/storage; redact values; fail with actionable missing inputs |
| `make dev MODE=sample` | Start local private stack with labelled fixtures and writes disabled |
| `make check` | Formatting, typing, docs/OpenAPI consistency, secret scan and unit suite |
| `make test-unit` | Fast domain/schema/oracle suite with no external credentials |
| `make test-integration` | Real DB, sidecar and adapters; credentialed groups report blocked separately |
| `make test-connected` | Actual Zetaris, H-MEM/embedding and model contracts; budgets enforced |
| `make test-e2e` | Browser/API/action persistence flow on allowlisted sandbox |
| `make eval` | Locked comparisons and manifest; refuses to expose heldout answers to optimizer |
| `make verify-docs` | Local links, OpenAPI drift, enum/command examples and source manifest |
| `make trial-profile-approve PROFILE=<reviewed-profile>` | Store authenticated, exact-scope authorization for a disposable trial fixture |
| `make memory-correction-preview` / `make memory-correction-apply` | Review and apply versioned correction using OPERATIONS contracts |
| `make demo` | Deterministic entry to selected connected scenario with explicit live/replay labels |

Never print a success banner when required checks were skipped. Compose reset removes only named demo data after explicit scope confirmation; it must not destroy existing datasets by default.

## Git and review

Initialize a team-owned repository only as part of an authorized implementation step. Preserve this pre-event baseline and declare it. Use short branches/worktrees per package; no force push or history rewriting to hide provenance. Commit coherent changes with code, tests, docs and evidence references. Future pushes/publications must match the user's authorization; the documentation task does not publish anything.

A PR should state the user-visible trigger and behavior, root cause when fixing a bug, changed contract, tests actually run, evidence artifacts and risks. Include failed/blocked checks honestly. A second builder reviews authorization, accounting, source fidelity and holdout boundaries when those change. Do not rely on a high coverage percentage for correctness.

Suggested review questions: Does the main path work end to end? Can source evidence be traced? Does reload preserve truth? Can a model or a stale client bypass authority? Are units/time/grain correct? Did this change alter a canonical API/doc? What does the real integration prove and what remains untested?

## Task handoff format

Each task closes with: scope and changed behavior; exact files/commits; reproduction or acceptance IDs; tests and integration environment; artifact/run IDs; blockers; next earliest unblocked item. Append actual event work to NEW_WORK.md. Update canonical docs when assumptions change and keep source reference files unmodified. A future agent should be able to resume without reconstructing decisions from chat history.
