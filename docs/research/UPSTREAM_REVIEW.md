## Architecture actually visible in source

The root Google ADK agent delegates to a sequential infrastructure advisor, forecasting agent, impact calculator, executor and summary agent. The advisor is a three-stage scout → profiler → recommender sequence. BigQuery provides records and `ML.FORECAST`; cost lookup scrapes a third-party pricing page; carbon comparison calls a Climatiq compute endpoint. The executor exposes stop/change-machine-type/start tools. A separate scheduled function appends perturbed metrics and recreates three ARIMA_PLUS models. Streamlit posts session and run requests to a hardcoded agent endpoint. Reports generate Google Docs, charts and presentations. These are static implementation observations; their current external-service compatibility is unknown. [Root agent](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agent.py#L14-L46), [advisor sequence](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/optimization_advisor_agent/agent.py#L1-L12), [frontend requests](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/Frontend/app.py#L155-L224), [summary flow](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/summary_generator_agent/agent.py#L18-L27).

The useful product idea is the closed loop from cloud evidence to proposed improvement to action and reporting. GreenOps Verify must add the missing proof and control boundaries. A bigger agent count alone does not establish a stronger system.

## Findings that change the new implementation

All links below refer to the reviewed immutable commit. Counterexamples are derived by inspection; they are proposed regression fixtures for our independently authored implementation, not claims that the upstream deployment was exercised.

| ID | Source observation and consequence | Requirement for GreenOps Verify |
|---|---|---|
| U01 — capacity validation | The safety function divides forecast sums by literal `7`, checks only average percentage thresholds and receives no target capacity. Empty lists therefore satisfy the numeric thresholds by inspection; a single 90% sample becomes about 12.86%. A low mean also cannot exclude damaging peaks after a resize. [Executor tools, lines 8–11](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/safe_executor_agent/tools.py#L8-L11). | Validate evidence completeness, timestamps, units and expected sample count; compare absolute CPU/memory demand and stress envelope against the proposed capacity. Reject missing data and incompatible targets. Keep these checks in deterministic code. |
| U02 — authorization and mutation boundary | Prompt instructions ask an LLM to run safety tools before the mutation, while the mutation itself directly stops, resizes and restarts the target. The shown mutation function has no plan-bound approval, target version check, action lock, idempotency record or recovery state. This identifies a source-level boundary gap; actual deployed IAM was not inspected. [Agent instructions/tools, lines 9–24](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/safe_executor_agent/agent.py#L9-L24), [mutation, lines 36–65](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/safe_executor_agent/tools.py#L36-L65). | Authenticated approval must bind actor, exact plan hash, target and policy versions, allowed operation and expiry. The executor must independently enforce it. Lock actions, use unique idempotency keys and reconcile uncertain provider outcomes before retrying. |
| U03 — verification and identity | The executor resolves a target by instance name within a fixed project, and its last check is provider state `RUNNING`. It does not read back the final machine type or run application health checks in the shown function. [Lookup, lines 13–21](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/safe_executor_agent/tools.py#L13-L21), [completion, lines 61–65](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/safe_executor_agent/tools.py#L61-L65). | Use provider/project/resource identity with zone and version where required. Re-read actual configuration and application health after execution. A running VM is insufficient for `VERIFIED`. |
| U04 — carbon duration mismatch | The carbon tool defaults to a 24-hour duration and sends that interval in both requests, but the agent prompt instructs a further multiplication by 24 for a daily delta. The profiler also multiplies returned totals by `24 × 30`. If the API totals cover the requested 24 hours, following these instructions introduces an extra 24-fold factor. Current API behavior was not tested. [Tool duration/payload, lines 76–101](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/impact_calculator_agent/agent.py#L76-L101), [daily formula, lines 177–192](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/impact_calculator_agent/agent.py#L177-L192), [monthly formula, lines 40–42](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/optimization_advisor_agent/sub_agents/workload_profiler_agent/agent.py#L40-L42). | Every impact record carries interval, quantity unit, method and factor version. Arithmetic belongs in tested code. The already-totalled 24-hour fixture must remain unchanged under a daily presentation. |
| U05 — carbon scenario collision | Carbon responses are keyed only by machine type. Comparing the same type in two regions writes both results under the same key. Missing component estimates default to zero. [Result mapping, lines 124–143](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/impact_calculator_agent/agent.py#L124-L143). | Assign scenario IDs and preserve provider, region, type, interval and units. Use `UNKNOWN` for absent measurements and factors. Test same-type/different-region scenarios and partial responses. |
| U06 — unbounded query interface | The scout and forecast tools accept arbitrary SQL strings and submit them directly to BigQuery. The scout retrieves all returned rows; its prompt asks for all rows when no filter is supplied. Source code does not show an allowlist, parameters, row budget or bytes-billed budget at these boundaries. This is not proof that the deployed role has write privileges. [Scout, lines 12–30](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/optimization_advisor_agent/sub_agents/infra_scout_agent/agent.py#L12-L30), [query instructions, lines 41–50](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/optimization_advisor_agent/sub_agents/infra_scout_agent/agent.py#L41-L50), [forecast query, lines 15–21](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/forecaster_agent/agent.py#L15-L21). | Expose finite, parameterized read-only Zetaris query templates with server-side authorization, row/deadline/cost limits and source receipts. Restrict underlying credentials too; string-prefix validation alone is insufficient. |
| U07 — compulsory recommendation | The profiler prompt requires a replacement type, suggests a 50% reduction when uncertain, permits CPU **or** memory thresholds to drive downsizing, and prioritizes particular instance-name prefixes. It permits recommendation even if savings tools fail. [Profiler, lines 25–65](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/optimization_advisor_agent/sub_agents/workload_profiler_agent/agent.py#L25-L65). | Allow `NEEDS_EVIDENCE` and justified `NO_CHANGE`. Require both CPU and memory capacity evidence, policy compatibility and trial results; never select targets because an identifier resembles a demo resource. |
| U08 — synthetic history and repeated snapshots | The scheduler uses `RAND()` to perturb current metrics before insertion, then trains forecasting models on that table. The shown insert has no per-resource/day upsert or duplicate guard. This is synthetic variation, not observed time-series telemetry; repeated runs may add another snapshot for the same day. [Snapshot, lines 9–60](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/Cloud%20Scheduler/Daily_Data_Snapshot_Model_Training/daily_data_snapshot.py#L9-L60), [training, lines 63–88](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/Cloud%20Scheduler/Daily_Data_Snapshot_Model_Training/daily_data_snapshot.py#L63-L88). | Label synthetic datasets, use seeded generation, preserve manifests and deduplicate event identities. Backtest against later held-out periods without leakage. Never claim forecast accuracy on real workloads from perturbed samples. |
| U09 — pricing provenance and deadlines | The impact tool scrapes an HTML table, selects a region by substring and returns a price string without currency/unit/effective-date fields. Its HTTP calls show no explicit timeout. [Price lookup, lines 38–72](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/impact_calculator_agent/agent.py#L38-L72), [carbon HTTP call, line 112](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/impact_calculator_agent/agent.py#L111-L119). | Use a verified provider catalogue or explicitly versioned price snapshot with SKU/region/currency/unit/effective interval. Distinguish catalogue estimates from actual marginal invoice savings. Bound external calls and preserve partial/unknown states. |
| U10 — report sharing and concurrent jobs | Report helpers grant `anyone` reader access to charts and documents. Chart filenames live in one shared `charts/` directory and the report deletes that directory afterward. These choices can expose sensitive reports and interfere across concurrent jobs. [Image sharing, lines 25–47](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/summary_generator_agent/tools/tools.py#L25-L47), [document sharing, lines 83–91](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/summary_generator_agent/tools/tools.py#L83-L91), [cleanup, line 146](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/summary_generator_agent/tools/tools.py#L140-L148), [shared path, lines 168–178](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agents/summary_generator_agent/tools/tools.py#L168-L178). | Private report exports by default; explicit publish operation if needed. Use per-investigation artifact storage, scoped URLs, retention policy and tenant-safe paths. |
| U11 — configuration and UI evidence | The root fetches two secrets during module import. Streamlit uses a fixed backend URL, requests with no explicit timeouts or authentication header in the shown client, and keeps only the last text part from the run response. These observations do not establish whether the deployment enforces separate authentication. [Import-time secrets, lines 8–12](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/agent.py#L8-L12), [frontend, lines 155–224](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/Frontend/app.py#L155-L224). | Lazy connector initialization, explicit validated configuration and least-privilege identities. UI must show durable investigation/action states, evidence receipts and failure outcomes, with bounded authenticated API calls. |

## Dependencies and verification evidence

The agent requirements file pins 135 packages, including `google-adk==1.0.0`, `fastapi==0.115.12` and `streamlit==1.46.0`; it is a flat requirements list, not an observed compatible clean-install environment. Frontend requirements leave Streamlit and Requests unpinned; the scheduler uses a wildcard Functions Framework version and unpinned BigQuery. The frontend Dockerfile uses a `python:3.12` tag and installs that unpinned frontend list. These facts establish reproducibility work is needed, not that any listed dependency has a confirmed vulnerability. [Agent requirements](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/greenops_agent/requirements.txt#L1-L135), [frontend requirements](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/Frontend/requirements.txt#L1-L2), [scheduler requirements](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/Cloud%20Scheduler/Daily_Data_Snapshot_Model_Training/requirements.txt#L1-L2), [Dockerfile](https://github.com/niksm7/GreenOps/blob/db38811fb653631892e6cbbe1275793bd9906858/Frontend/Dockerfile#L1-L9).

Do not inherit these pins as the new baseline. Select a minimal dependency set after real sponsor/model smoke tests, resolve and commit compatible lockfiles, document runtime versions and run a current advisory audit during implementation. No dependency installation or vulnerability scan was performed in this review.

The full tree includes `.env`, `.DS_Store`, compiled Python, a zip archive, screenshots and a presentation template. Their presence is a repository-hygiene signal; it does **not** prove a secret was leaked. Do not copy them. Our repository should ignore secrets/build artifacts and scan its own staged changes. ## How the review maps into the build

1. Implement the evidence, cost/carbon and capacity contracts before LLM coordination. U01, U04–U09 become regression fixtures with independently authored test data.
2. Deliver genuine Zetaris queries over independent sources with source receipts. Avoid merely replacing a BigQuery function name while retaining arbitrary model SQL.
3. Add real Meterless H-MEM behind a private persistent adapter. Keep approval, locks and action state transactional in PostgreSQL; retrieval must not grant authority.
4. Make the critic reject one evidence-deficient or workload-failing candidate and trigger a bounded revision. Valid `NO_CHANGE` is part of the product.
5. Implement U02–U03 as an authenticated action state machine; first prove duplicate, stale, expired and unknown-outcome cases in a disposable environment.
6. Demonstrate measured before/after workload behavior, durable state after reload and honest impact accounting. Finish with private, reproducible evidence export and an explicit limitations panel.

The minimum acceptance suite is already outlined in the supplied handoff. This review reinforces it with exact upstream source locations. Passing tests in the new implementation must be recorded separately; this document does not mark any runtime feature, sponsor integration or safety property as implemented.
